# PA-Container 2.0: Agentic Software Factory Architecture & Implementation Plan

* **Status:** Architecture Specification & Refactoring Plan (RFC)
* **Target Repository:** `https://github.com/mikkovihonen/pa-container`
* **Core Subsystems Affected:** `pa` CLI, `pa_core`, `pa_packages`, `coding-agent`, `coding-agent-proxy`
* **Target Environments:** macOS Desktop (Apple Silicon), Linux Desktop, Linux Server / Cloud Platforms

---

## 1. Executive Summary & Vision

`pa-container` began as a rootless Podman-based sandbox designed to launch an autonomous coding agent (`pi`, `opencode`, `antigravity`, or `claude`) inside a developer's local project directory (`cd /path/to/project && pa run`). By bind-mounting the host directory into a Fedora-based container attached to an `--internal` Podman network, `pa-container` guarantees that all HTTP, HTTPS, and DNS traffic traverses `coding-agent-proxy` (`mitmproxy`), enforcing hostname allowlists, placeholder token replacement, and complete flow export auditing.

The next evolutionary leap for `pa-container` is to transform from a **single-directory container wrapper** into a portable **Agentic Software Factory**:

1. **Rapid Desktop Prototyping:** Developers can compose, test, and iterate on multi-agent software factory capabilities on their desktop (macOS or Linux)—including GPU-accelerated server workloads, local LLM inference (`llama-server`), Media ACPs (Agent Communication Protocol tools), headless virtual desktops (`agent-desktop`), and mobile app toolchains (iOS & Android).
2. **Zero-Rewrite Cloud Promotion:** Once a factory configuration proves effective on the desktop, the exact same declarative factory blueprint can be deployed to a Linux server or cloud environment without architectural translation.
3. **Uncompromised Network Introspection:** Every network packet generated by any agent, build tool, GPU service, or mobile simulator/emulator continues to be routed through an external `coding-agent-proxy` instance with per-agent identity attribution.

## 2. Assessment of the Current `pa-container` (v0.7.x) Architecture

### 2.1. Current Subsystem Inventory

Following the recent repository restructuring (`src/` $\rightarrow$ `pa_core/`, `packages/` $\rightarrow$ `pa_packages/`) and feature additions (`feat: media acps`, `t3-code`, multi-agent synthesis), the project consists of:

* **`pa` & `pa_core/`:** Python orchestration engine managing workspace initialization (`pa init`), image building (`pa build`, `pa build --llama`), container lifecycle (`pa run`, `pa clean`), log inspection (`pa logs`), virtual desktop endpoints (`pa desktop`), and proxy queries (`pa proxy`). Includes reference-counted lifecycle management for shared host services.
* **`coding-agent-proxy/`:** Containerized `mitmproxy` (`mitmweb` / `mitmdump`) running custom Python addons:
    * **Allowlist Addon:** Filters egress HTTP/HTTPS requests and DNS queries (`:53`) by hostname/wildcard rules.
    * **Token Replacer Addon:** Substitutes placeholder credentials inside the agent environment with real secrets stored in the host `keyring` at the proxy boundary, preventing credential exfiltration by prompt-injected agents.
    * **Flow Export Addon:** Records full request/response streams to per-project `.mitm` audit files.
* **`coding-agent/`:** Fedora-based runtime image housing the core system environment, optional headless display stacks (**Wayland** via `labwc` + `wayvnc` + `noVNC`, or **X11** via `Xvfb` + `openbox` + `x11vnc`), `agent-desktop` UI automation CLI with **Chrome for Testing**, and **T3 Code** web interface integration (with Tailscale and Cloudflare tunnel support).
* **`pa_packages/`:** Pluggable, on-demand toolchain staging, agent drivers (`pi`, `opencode`, `antigravity`, `claude`), dynamic provider configuration synthesis, and the newly introduced **Media ACPs**.

### 2.2. Four Architectural Bottlenecks Blocking the "Software Factory" Goal

1. **The Apple Silicon Hypervisor Barrier (GPU & Mobile on macOS):**
   On macOS, Podman runs Linux containers inside a Linux virtual machine (`podman machine` over `Virtualization.framework`). Apple's hypervisor does **not** expose Metal, the Apple Neural Engine (ANE), PyTorch `mps`, or Apple MLX to Linux guest VMs. While `pa-container` works around this for text inference by running `llama-server` directly on the macOS host, agents inside the Fedora container cannot run native Apple GPU compute workloads, nor can they build or test iOS applications (`xcodebuild` and `iOS Simulator` require a macOS kernel and Aqua `WindowServer`).
2. **Host Bind-Mount Coupling (`cd /project && pa run`):**
   Mounting a host working directory directly into the container ties the execution model to the developer's laptop filesystem:
    * On macOS, `virtiofs` bind-mounts suffer severe I/O degradation during heavy dependency builds (`node_modules`, `.venv`, Rust `target/`) and require complex `keep-id` UID/GID mapping.
    * It conflates the **Factory Blueprint** (agents, toolchains, ACPs, proxy policies) with the **Target Codebase**.
    * Cloud environments do not have a developer's local directory to bind-mount; cloud factories ingest tasks via Git repositories and webhooks.
    * Multiple agents operating concurrently on a single bind-mounted directory collide on file locks, build artifacts, and Git index states.
3. **Per-Workspace Container Duplication Overhead:**
   Currently, spinning up multiple isolated agents requires launching separate container pairs (`coding-agent` + `coding-agent-proxy`) and isolated Podman networks, multiplying memory overhead for base OS processes, display servers, and toolchains.
4. **Direct Podman CLI Coupling in `pa_core`:**
   Orchestrating containers by directly invoking `podman` subprocesses inside `pa_core` locks the runtime to single-node container semantics rather than VM-level isolation required for multi-tenant cloud deployments and macOS guest virtualization.

## 3. Target Architecture: 3-Tier Factory VM + Multi-User OS Sandboxes + External Proxy

To solve all four bottlenecks while preserving every existing strength of `pa-container`, the target architecture replaces the single-container bind-mount model with a **Three-Tier Isolation Model**:

1. **Tier 1 — External `coding-agent-proxy` (Host / Control Plane):** The `mitmproxy` security boundary remains strictly **outside** the Factory VM. Even a total kernel or root compromise inside the Factory VM cannot access `keyring` secrets, bypass the allowlist, or alter exported `.mitm` audit logs.
2. **Tier 2 — The Factory VM ("The Factory Floor"):** A hardware-virtualized guest OS providing kernel isolation and native GPU access:
    * **On macOS Desktop:** A macOS Guest VM powered by **Tart** (`Virtualization.framework`), providing paravirtualized Metal GPU ($\approx 92\%$ native speed), MLX, Xcode, and iOS Simulator.
    * **On Linux Desktop & Server/Cloud:** A Linux Guest VM powered by **Incus VM** or **Cloud Hypervisor** (or a native Cloud VM instance in production) with KVM isolation and direct VFIO / Virtio-GPU (`/dev/dri`, `/dev/nvidia*`) passthrough.
3. **Tier 3 — Multi-User POSIX Workstations + OS Process Sandboxes ("The Workbenches"):** Inside the Factory VM, each coding agent runs as a dedicated, unprivileged POSIX user (`agent1` with $\text{UID } 2001$, `agent2` with $\text{UID } 2002$, etc.) wrapped in an OS-native mandatory access control sandbox (**Seatbelt `sandbox-exec`** on macOS; **Bubblewrap `bwrap` + Landlock** on Linux) over an instant Copy-on-Write (CoW) Git clone.

### 3.1. Cross-Platform Architectural Mapping

| Layer | macOS Desktop (Apple Silicon) | Linux Desktop & Cloud Server | Architectural Purpose |
| :--- | :--- | :--- | :--- |
| **1. Outer VM Engine** | **Tart** (`Virtualization.framework`) | **Incus VM** / **Cloud Hypervisor** / Cloud VM | Kernel boundary, GPU passthrough, fast OCI/CoW image cloning |
| **2. Hypervisor Network Gate** | **Softnet** (`--net-softnet-allow`) | **Linux Bridge + Host `nftables`** | Drops any packet from the VM not destined for `coding-agent-proxy` |
| **3. Guest Firewall (UID Routing)** | **macOS `pf`** (`user <uid>`) | **Linux `nftables`** (`meta skuid <uid>`) | Routes each agent user's traffic to its dedicated proxy port |
| **4. OS User Isolation** | POSIX User (`dscl`, $\text{UID} \ge 2001$) | POSIX User (`useradd`, $\text{UID} \ge 2001$) | Process tree, memory space, IPC, and file permission isolation |
| **5. Process Sandbox** | **Seatbelt** (`sandbox-exec -f`) | **Bubblewrap** (`bwrap`) + **Landlock** | Write-jail to `/home/agentN` and outbound socket lock to proxy port |
| **6. GPU Acceleration** | Paravirtualized **Metal**, MLX, PyTorch `mps` | **VFIO / Virtio-GPU** (`/dev/dri`, `/dev/nvidia*`), CUDA, ROCm, Vulkan | Native hardware acceleration for ML, Media ACPs, and rendering |
| **7. Workspace Filesystem** | **APFS** (`cp -c -R` CoW clone) | **Btrfs / XFS / ZFS** (`cp --reflink=always`) | Instant, zero-duplication per-agent Git worktree clones |
| **8. Toolchain Staging** | Shared read-only `/opt/pa/packages` | Shared read-only `/opt/pa/packages` | On-demand `pa_packages` mounted read-only into all agent sandboxes |

## 4. Network Architecture & Multi-Agent `coding-agent-proxy` (Option A)

Keeping `coding-agent-proxy` outside the Factory VM creates a fundamental routing challenge: standard TCP/IP packets leaving a VM do not carry the guest OS user ID ($\text{UID}$) that originated them. **Option A** solves this cleanly and deterministically using **UID-to-Port Mapping**:

* `coding-agent-proxy` listens on a dedicated port per active agent slot ($8081 \rightarrow \text{agent1}$, $8082 \rightarrow \text{agent2}$, ..., $8080 + N \rightarrow \text{agent}N$).
* The guest OS kernel firewall (`pf` or `nftables`) matches outbound packets by the originating socket's kernel $\text{UID}$ and permits/redirects traffic **only** to that specific user's assigned port on the external proxy.

### 4.1. Three-Layer Defense-in-Depth Network Lockdown

#### Layer 1: Hypervisor-Level Egress Filter (Outside the VM)

* **On macOS (Tart + Softnet):**
  Tart launches the VM connected to Softnet restricted strictly to the host IP of `coding-agent-proxy`:
  ```bash
  tart run \
    --net-softnet \
    --net-softnet-allow="${PROXY_HOST_IP}/32" \
    --no-clipboard \
    --no-audio \
    pa-factory-macos:latest
  ```
  Even if an attacker compromises root inside the macOS guest VM and flushes `/etc/pf.conf`, the hypervisor drops every packet sent to any IP address other than `${PROXY_HOST_IP}`.
* **On Linux (Incus / KVM Bridge + Host `nftables`):**
  The Factory VM attaches to an internal bridge (`pa-br0`) with no default IP forwarding enabled on the host. Host `nftables` allows traffic from `pa-br0` solely to the `coding-agent-proxy` container/process IP on ports $5353$ and $8080\text{--}8099$.

#### Layer 2: Guest OS Kernel Firewall (UID-to-Port Enforcement)

* **macOS Guest VM (`/etc/pf.conf`):**
  Loaded and locked by the guest daemon (`pa-agentd`) at boot, with IPv6 disabled (`networksetup -setv6off Ethernet`):
  ```pf
  # Macros injected by pa-agentd
  proxy_ip = "192.168.64.1"
  dns_port = "5353"

  set block-policy return
  set skip on lo0

  # Default deny all outbound and inbound traffic
  block in all
  block out all

  # Allow inbound SSH/control only from the host gateway to pa-agentd
  pass in quick proto tcp from $proxy_ip to any port 2222 keep state

  # Allow DNS queries ONLY to coding-agent-proxy DNS listener
  pass out quick proto { tcp, udp } from any to $proxy_ip port $dns_port user { _pa_daemon, agent1, agent2, agent3, agent4 } keep state

  # Strict UID-to-Proxy-Port lockdown per agent user
  pass out quick proto tcp from any to $proxy_ip port 8080 user _pa_daemon keep state
  pass out quick proto tcp from any to $proxy_ip port 8081 user agent1 keep state
  pass out quick proto tcp from any to $proxy_ip port 8082 user agent2 keep state
  pass out quick proto tcp from any to $proxy_ip port 8083 user agent3 keep state
  pass out quick proto tcp from any to $proxy_ip port 8084 user agent4 keep state
  ```

* **Linux Guest VM (`/etc/nftables.conf`):**
  On Linux, `nftables` provides both strict port filtering (`8081..8084` for explicit `HTTP_PROXY` clients) **and** transparent `DNAT` redirection (`8091..8094` in `--mode transparent`) for binaries that ignore `HTTP_PROXY` environment variables:
  ```nft
  flush ruleset

  define PROXY_IP = 10.240.0.1
  define DNS_PORT = 5353

  table ip pa_factory {
      chain nat_output {
          type nat hook output priority -100; policy accept;

          # Do not redirect traffic targeting localhost or already targeting the proxy IP
          ip daddr 127.0.0.0/8 return
          ip daddr $PROXY_IP return

          # Redirect all direct DNS traffic from agents to coding-agent-proxy DNS
          meta skuid >= 2001 udp dport 53 dnat to $PROXY_IP:$DNS_PORT
          meta skuid >= 2001 tcp dport 53 dnat to $PROXY_IP:$DNS_PORT

          # Redirect direct HTTP/HTTPS calls (tools ignoring HTTP_PROXY) to transparent proxy ports
          meta skuid "agent1" tcp dport { 80, 443 } dnat to $PROXY_IP:8091
          meta skuid "agent2" tcp dport { 80, 443 } dnat to $PROXY_IP:8092
          meta skuid "agent3" tcp dport { 80, 443 } dnat to $PROXY_IP:8093
      }

      chain filter_output {
          type filter hook output priority 0; policy drop;

          oifname "lo" accept
          ct state established,related accept

          # Allow DNS to proxy
          meta skuid { "_pa_daemon", "agent1", "agent2", "agent3" } ip daddr $PROXY_IP udp dport $DNS_PORT accept
          meta skuid { "_pa_daemon", "agent1", "agent2", "agent3" } ip daddr $PROXY_IP tcp dport $DNS_PORT accept

          # Allow each agent UID ONLY to its own regular (808N) and transparent (809N) proxy ports
          meta skuid "_pa_daemon" ip daddr $PROXY_IP tcp dport 8080 accept
          meta skuid "agent1" ip daddr $PROXY_IP tcp dport { 8081, 8091 } accept
          meta skuid "agent2" ip daddr $PROXY_IP tcp dport { 8082, 8092 } accept
          meta skuid "agent3" ip daddr $PROXY_IP tcp dport { 8083, 8093 } accept
      }
  }
  ```

#### Layer 3: Process Sandbox Network Enforcement

* Both the macOS Seatbelt profile and the Linux Landlock wrapper restrict the agent process tree so that `connect()` syscalls are only permitted to `127.0.0.1:*` (for local dev servers/test runners) and `$PROXY_IP:$AGENT_PORT`.

### 4.2. Upgrading `coding-agent-proxy` Addons for Multi-Agent Identity

Currently, `coding-agent-proxy` assumes a 1:1 mapping between a proxy instance and a single workspace/agent. In `pa-container` 2.0, a single `coding-agent-proxy` instance serves the entire Factory VM by binding multiple listening ports and resolving the agent profile via `flow.client_conn.sockname[1]`.

```python
# coding-agent-proxy/addons/multi_agent_context.py
from dataclasses import dataclass
from mitmproxy import http, dns

@dataclass
class AgentPolicy:
    agent_id: str
    user: str
    driver: str
    allowed_hosts: list[str]
    token_placeholders: dict[str, str]  # placeholder -> actual secret from keyring
    flow_log_path: str

class MultiAgentContextAddon:
    def __init__(self, port_map: dict[int, AgentPolicy]) -> None:
        self.port_map = port_map

    def _resolve_policy(self, local_port: int) -> AgentPolicy | None:
        return self.port_map.get(local_port)

    def requestheaders(self, flow: http.HTTPFlow) -> None:
        _, local_port = flow.client_conn.sockname[:2]
        policy = self._resolve_policy(local_port)
        if policy is None:
            flow.response = http.Response.make(403, b"PA-Proxy: Unregistered agent port\n")
            return

        # Attach identity metadata for downstream addons (Allowlist, TokenReplacer, FlowExport)
        flow.metadata["pa_agent_id"] = policy.agent_id
        flow.metadata["pa_agent_user"] = policy.user
        flow.metadata["pa_agent_driver"] = policy.driver
        flow.metadata["pa_policy"] = policy
```

* **Allowlist Addon Update (`docs/proxy/allowlist.md`):** Reads `flow.metadata["pa_policy"].allowed_hosts`. A frontend agent can be permitted access to `registry.npmjs.org`, while a code-review agent is restricted strictly to `api.anthropic.com`.
* **Token Replacer Addon Update (`docs/proxy/token-replacer.md`):** Placeholder tokens injected into an agent's environment (e.g., `PA_PLACEHOLDER_AGENT1_GITHUB_TOKEN`) are only replaced if they match `flow.metadata["pa_policy"].token_placeholders`. `agent2` cannot trick the proxy into substituting `agent1`'s credentials.
* **Flow Export Addon Update (`docs/proxy/flow-export.md`):** Writes both a unified factory flow stream (tagged with `pa_agent_id` for inspection in `mitmweb`) and per-agent audit streams (`flows-agent1.mitm`), surfaced via `pa logs --agent agent1`.

## 5. Inner Isolation: Multi-User POSIX Workstations & Native Sandboxes

Inside the Factory VM, `pa-agentd` manages a pool of unprivileged POSIX accounts (`agent1` = $\text{UID } 2001$, `agent2` = $\text{UID } 2002$, etc.) with directory permissions `0700` on `/Users/agentN` (macOS) or `/home/agentN` (Linux).

### 5.1. Shared `pa_packages` Toolchain Mounting

In `pa-container` v0.7.x, on-demand toolchains (`pa_packages`) are built into container image layers. In the Factory VM model, `pa_packages` builds self-contained, immutable toolchain trees under `/opt/pa/packages/<package-name>-<hash>/` owned by `root:_pa_daemon` with `0755` permissions:

* All agents share the exact same compilers, runtimes (Node, Python/`uv`, Rust, Go, Android SDK), agent CLIs (`pi`, `opencode`, `antigravity`, `claude`), and Media ACP binaries in read-only mode without disk duplication.
* Agent-specific mutable caches (`NPM_CONFIG_CACHE`, `UV_CACHE_DIR`, `CARGO_HOME`, `GOPATH`) are redirected into `/home/agentN/.cache`.

### 5.2. macOS Guest Sandbox: Seatbelt (`sandbox-exec`)

When launching an agent inside the macOS Tart VM, `pa-agentd` synthesizes `/etc/pa/profiles/agent1.sb` and executes the agent under `sandbox-exec`:

```scheme
(version 1)
(allow default)

;; 1. Strict Network Lockdown: Only loopback and dedicated external proxy port (8081)
(deny network*)
(allow network-outbound (remote tcp "192.168.64.1:8081"))
(allow network-outbound (remote udp "192.168.64.1:5353"))
(allow network-outbound (remote tcp "192.168.64.1:5353"))
(allow network-outbound (remote unix-socket))
(allow network-inbound (local ip "localhost:*"))
(allow network-outbound (remote ip "localhost:*"))

;; 2. Cross-User & Vault Read Protection
(deny file-read*
    (subpath "/Users/admin")
    (subpath "/Users/agent2")
    (subpath "/Users/agent3")
    (subpath "/Users/agent4")
    (subpath "/private/var/pa-vault")
    (subpath "/etc/pa/profiles"))

;; 3. Filesystem Write Jail: Agent can ONLY write to its own home & temp dirs
(deny file-write*)
(allow file-write*
    (subpath "/Users/agent1")
    (subpath "/private/tmp/pa-agent1")
    (subpath "/private/var/folders")
    (literal "/dev/null")
    (literal "/dev/zero")
    (literal "/dev/random")
    (literal "/dev/urandom")
    (literal "/dev/dtracehelper"))

;; 4. Allow Paravirtualized Metal GPU, CoreML, and IOKit Compute Access
(allow iokit-open
    (iokit-user-client-class "AGXDeviceUserClient")
    (iokit-user-client-class "AGXSharedUserClient")
    (iokit-user-client-class "IOSurfaceRootUserClient")
    (iokit-user-client-class "AppleKeyStoreUserClient"))
```

### 5.3. Linux Guest Sandbox: Bubblewrap (`bwrap`) + Landlock + `cgroups v2`

On the Fedora-based Linux Factory VM, `pa-agentd` places each agent inside a dedicated systemd scope (`systemd-run --slice=pa-agents.slice -p MemoryMax=8G -p CPUWeight=100 --uid=agent1`) and wraps execution in `bwrap` + a small Landlock helper (`pa-landlock-run`):

  --unshare-uts \
  --die-with-parent \

  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /etc/resolv.conf /etc/resolv.conf \
  --ro-bind /etc/pki /etc/pki \
  --ro-bind /etc/ssl /etc/ssl \
  --ro-bind /opt/pa /opt/pa \
  --proc /proc \
  --dev /dev \
  --dev-bind-try /dev/dri /dev/dri \

  --dev-bind-try /dev/nvidia-uvm /dev/nvidia-uvm \
  --tmpfs /tmp \
  --tmpfs /run \
  --tmpfs /home \
  --bind /home/agent1 /home/agent1 \
  --chdir /home/agent1/workspace \
  --setenv HOME /home/agent1 \
  --setenv USER agent1 \
  --setenv HTTP_PROXY http://10.240.0.1:8081 \
  --setenv HTTPS_PROXY http://10.240.0.1:8081 \
  --setenv SSL_CERT_FILE /opt/pa/certs/mitmproxy-ca-cert.pem \
  --setenv NODE_EXTRA_CA_CERTS /opt/pa/certs/mitmproxy-ca-cert.pem \

    --rw-path /tmp \

## 6. Workspace Management: Replacing Bind-Mounts with Git Vault, CoW Clones & IDE Bridges

To make the Software Factory portable between desktop and cloud while supporting fast local IDE code review, host directory bind-mounts are replaced by a **Git Vault + Copy-on-Write (CoW) Workspace** architecture.

```
[Developer Host Repository]               [Factory VM: /var/pa-vault/repo.git]
 (macOS / Linux Desktop)   <--- git --->   (Owned by _pa_daemon, Bare Git Vault)
         |                                          |                    |
  pa review agent1                         CoW Clone (APFS/Btrfs)  CoW Clone (APFS/Btrfs)
  (git worktree add                                 v                    v
   .pa/review/agent1)                     [/home/agent1/workspace] [/home/agent2/workspace]
                                           Branch: pa/agent1/task   Branch: pa/agent2/task
```

### 6.1. The Internal Git Vault & Instant CoW Provisioning

1. **Ingestion (`pa run` or `pa task submit`):**
    * **On Desktop:** When the user runs `pa run` inside a local Git repository, `pa_core` pushes the current HEAD (plus any staged/uncommitted working tree state as a temporary commit on `refs/pa/ingest/head`) over the SSH control channel into `/var/pa-vault/<project>.git` inside the Factory VM.
    * **In the Cloud:** `pa-agentd` clones the repository directly from GitHub/GitLab through `coding-agent-proxy` into `/var/pa-vault/<project>.git`.
2. **Master Reference Checkout:**
    * `_pa_daemon` maintains a clean, read-only reference checkout (including pre-warmed dependency caches if configured) at `/var/pa-vault/checkouts/<project>-main`.
3. **Millisecond Copy-on-Write Agent Clone:**
    * When `agent1` starts a task, `pa-agentd` clones `/var/pa-vault/checkouts/<project>-main` into `/home/agent1/workspace` using filesystem-level Copy-on-Write:
    * **macOS (APFS):** `cp -c -R /var/pa-vault/checkouts/proj-main /Users/agent1/workspace`
    * **Linux (Btrfs / XFS / ZFS):** `cp --reflink=always -a /var/pa-vault/checkouts/proj-main /home/agent1/workspace`
    * Ownership is set to `chown -R agent1:agent1`, and a new branch `pa/agent1/<task-id>` is checked out.
4. **Branch-Scoped Local Git Remote:**
    * Inside `/home/agent1/workspace`, the `origin` remote points to a lightweight local Git HTTP daemon (`http://127.0.0.1:9418/<project>.git`) run by `_pa_daemon`.
    * Pre-receive hooks verify the peer socket / token so `agent1` can fetch all branches but can **only** push to `refs/heads/pa/agent1/*`.

### 6.2. Developer IDE Code Review & Live Inspection on Desktop

Even though agents work inside isolated VM storage, developers have three seamless ways to review, edit, and test agent code in their local IDE (VS Code, Cursor, Zed, Xcode, Android Studio):

1. **Local Git Worktree Bridge (`pa review <agent-id>`):**
    * `pa_core` automatically fetches `refs/heads/pa/<agent-id>/*` from the Factory VM Vault into the host repository's `.git/refs/remotes/pa/<agent-id>/*`.
    * Running `pa review agent1` executes `git worktree add .pa/review/agent1 pa/agent1/<branch>` on the host and optionally opens the user's IDE (`--open`).
    * Because `.pa/review/agent1` is a native directory on the host filesystem, the developer can inspect diffs, run host-side tools, or merge changes (`pa merge agent1`) without disturbing their main working tree.
2. **Direct IDE Remote Connection (`pa ide <agent-id>`):**
    * Configures an SSH host alias (`pa-factory-agent1`) and launches VS Code / Cursor Remote-SSH directly attached to `/home/agent1/workspace` inside the VM.
3. **Live Two-Way Background Sync (`pa sync <agent-id>`):**
    * When a developer wants live file synchronization between `/Users/agent1/workspace` in the VM and `.pa/review/agent1` on the host (for example, while keeping an IDE open side-by-side with T3 Code), `pa` spawns a Mutagen sync session over the SSH control channel—achieving native filesystem speeds on both sides without `virtiofs` mount bottlenecks.

## 7. GPU Workloads, Media ACPs, Mobile (iOS/Android), and Virtual Desktop

### 7.1. GPU Server Workloads & Local LLM / Media ACP Architecture

`pa-container` 2.0 supports two complementary GPU execution patterns depending on workload memory characteristics:

#### Pattern 1: In-Sandbox Direct GPU Execution (Application & ML Testing)

When an agent is developing or testing a GPU-accelerated server workload (e.g., a PyTorch inference microservice, custom Metal/CUDA kernels, Vulkan rendering pipeline, or WebGPU backend):

* **On macOS (Tart VM):** The agent runs Python/`uv` or Swift binaries directly inside its Seatbelt sandbox. Apple's paravirtualized Metal device is accessible via `torch.device("mps")`, Apple `mlx`, and `ggml-metal`.
* **On Linux (Incus / Cloud VM):** The agent runs CUDA, ROCm, or Vulkan workloads directly inside its `bwrap` sandbox using the bound `/dev/nvidia*`, `/dev/kfd`, and `/dev/dri` devices.
* **Testing Locally from the Host Browser/CLI:** `pa-agentd` exposes a controlled port-forward command (`pa port-forward agent1 8000:8000`) so the developer can hit the GPU server running inside `agent1`'s sandbox directly from `localhost:8000` on the host.

#### Pattern 2: Shared Compute Plane (`llama-server` & Media ACPs)

Heavy foundation models (such as a 30B+ parameter `llama-server` model or large diffusion/audio models used by `feat: media acps`) should not be duplicated in VRAM by every concurrent agent user:

* **Refcounted Host / VM Compute Plane:** Just as `pa-container` currently runs `llama-server` on the host shared via configuration fingerprint and refcounting, both `llama-server` and heavy **Media ACP servers** run as shared services on the host (macOS Desktop) or in the shared `_pa_daemon` service slice (Linux Server/Cloud).
* **Mandatory Proxy Routing for ACPs & Local LLMs:** Agents do not connect to `llama-server` or Media ACPs via unix sockets or unmonitored localhost ports. Instead, they connect via virtual hostnames (e.g., `http://llama.pa.internal` and `http://media-acp.pa.internal`) routed **through `coding-agent-proxy`**.
* **Full Auditability:** Because local LLM inference and Media ACP tool invocations pass through `coding-agent-proxy`, every prompt, tool call, and generated media payload is recorded in the agent's `.mitm` flow log.

### 7.2. Mobile Application Development & Testing (iOS & Android)

#### iOS Development & Simulator Bridge (macOS Tart Factory VM)

On macOS, command-line builds (`swift build`, `xcodebuild -scheme App -sdk iphonesimulator`) work directly inside unprivileged background user sessions (`agent1`, `agent2`). However, `Simulator.app` and `SimRenderServer` require access to the active graphical macOS Aqua session (`WindowServer`, owned by the logged-in GUI user `admin`, $\text{UID } 501$).

To bridge background coding agents to `iOS Simulator` securely:

1. **Auto-Logged-In Aqua Session (`admin`, $\text{UID } 501$):** The Tart macOS VM boots into an auto-logged-in headless graphical session running `pa-ios-runnerd`.
2. **Per-Agent Simulator Provisioning:** When `agent1` requests an iOS target, `pa-ios-runnerd` clones a clean iOS Simulator device (`xcrun simctl create pa-agent1-iphone "iPhone 16 Pro"`) dedicated to `agent1`.
3. **Automatic `mitmproxy` Root Certificate Injection:**
   `pa-ios-runnerd` injects the external `coding-agent-proxy` CA certificate directly into the simulator's trusted root store:
   ```bash
   xcrun simctl keychain <SIM_UDID> add-root-cert /opt/pa/certs/mitmproxy-ca-cert.pem
   ```
4. **Network Attribution for Simulator Traffic:**
   The simulator instance is launched with proxy environment settings pointing to `agent1`'s dedicated proxy port (`192.168.64.1:8081`). Every HTTPS API call made by the iOS app under test is intercepted by `coding-agent-proxy`, checked against `agent1`'s allowlist, and logged in `flows-agent1.mitm`.
5. **iOS Simulator ACP Tool (`pa-ios-acp`):**
   `agent1` interacts with its assigned simulator through an ACP server over a local Unix socket (`/var/run/pa-ios/agent1.sock`), exposing structured tools:
    * `ios_build_and_install` (builds `.app` bundle and runs `simctl install` + `simctl launch`)
    * `ios_screenshot` & `ios_accessibility_tree` (integrating with `agent-desktop` semantics)
    * `ios_tap`, `ios_type`, `ios_swipe`
    * `ios_logs` (streams unified logging `simctl spawn <UDID> log stream` filtered to the app bundle ID)
    * `ios_xctest` (executes `xcodebuild test-without-building`)

#### Android Development & Emulator Bridge (macOS & Linux VMs)

* Each agent user can build Android APKs via Gradle inside its sandbox and launch a headless, hardware-accelerated Android Emulator instance directly under its own $\text{UID}$:
  ```bash
  emulator -avd pa_agent1_api35 \
    -gpu host \
    -no-window \
    -no-audio \
    -http-proxy http://${PROXY_IP}:${AGENT_PORT} \
    -port 5554
  ```
* Because the `emulator` process runs as `agent1` ($\text{UID } 2001$), guest firewall rules (`pf` / `nftables`) automatically guarantee that all emulator traffic is locked to `agent1`'s proxy port (`8081`).

### 7.3. Headless Virtual Desktop (`agent-desktop`) & T3 Code Integration

* **Per-Agent Headless Wayland / X11 on Linux VM:**
  Inside the Linux Factory VM, any agent user (`agent1`, `agent2`) can start the existing `pa-container` virtual display stack (`labwc` + `wayvnc` + `noVNC` + `agent-desktop` + Chrome for Testing) inside its `bwrap` namespace using `/dev/dri` hardware acceleration.
* **T3 Code Web UI & Remote Tunnels (`docs/t3-code.md`):**
  T3 Code runs inside the Factory VM per workspace/agent, with `pa-agentd` mapping its web port back to the host. Existing CLI flags (`pa run --t3`, `pa desktop -o`, and Tailscale/Cloudflare tunnel advertisements) continue to work identically from the user's perspective.

### 9.2. Core Python Interfaces (`pa_core/backends/base.py`)

```python
from abc import ABC, abstractmethod
from pathlib import Path
from pa_core.config.factory_schema import FactoryConfig, AgentSpec

class FactoryBackend(ABC):
    """Abstract runtime provider for managing a Software Factory environment."""

    @abstractmethod
    def start_proxy(self, config: FactoryConfig) -> str:
        """Start external coding-agent-proxy listening on all configured agent ports."""

    @abstractmethod
    def ensure_factory_vm(self, config: FactoryConfig, proxy_ip: str) -> None:
        """Boot or update the Factory VM (Tart, Incus, or Cloud VM) with hypervisor network lock."""

    @abstractmethod
    def sync_git_to_vault(self, host_repo: Path, branch: str) -> str:
        """Push host Git state into the Factory VM's /var/pa-vault bare repository."""

    @abstractmethod
    def launch_agent(self, agent: AgentSpec, task_prompt: str | None = None) -> int:
        """Instruct pa-agentd to create user/CoW clone, apply firewall/sandbox, and start agent."""

    @abstractmethod
    def fetch_agent_branch(self, agent_id: str, host_repo: Path) -> str:
        """Fetch agent's branch from Factory VM Vault into host .git and create review worktree."""

    @abstractmethod
    def stop_factory(self) -> None:
        """Gracefully stop all agent sandboxes, shut down Factory VM, and release refcounts."""
```

## 10. Phased Implementation Roadmap

### Phase 1: Backend Abstraction & Multi-Port `coding-agent-proxy`

* Extract direct `podman` subprocess calls in `pa_core` into `pa_core/backends/podman_legacy.py` behind the `FactoryBackend` protocol so all existing `pytest` suites and `pa run` workflows pass without regression.
* Upgrade `coding-agent-proxy` addons (`allowlist`, `token_replacer`, `flow_export`) to support multiple listening ports (`8081..8099` and `8091..8099`) mapped to individual `AgentPolicy` objects via `multi_agent_context.py`.
* Update `pa logs` and `pa proxy` to display per-agent port mappings and filter `.mitm` flows by `pa_agent_id`.

### Phase 2: `pa-agentd`, Git Vault & Linux KVM/Incus Backend

* Implement `pa_core/guest_daemon/` (`pa-agentd`), including automated creation of POSIX users ($\text{UID} \ge 2001$), `/etc/nftables.conf` UID-to-port generation, and `bwrap` + Landlock sandboxing.
* Build the Fedora Factory VM image reusing the existing `coding-agent/` Fedora package definitions and `pa_packages/` staging scripts.
* Implement `/var/pa-vault` with `cp --reflink=always` CoW workspace cloning and add `pa review <agent-id>` on the host to create local `git worktree` checkouts for IDE inspection.
* Implement `IncusLinuxBackend` with `/dev/dri` and `/dev/nvidia*` GPU passthrough.

### Phase 3: macOS Tart + Softnet + Seatbelt + iOS Simulator ACP

* Implement `TartMacOSBackend` in `pa_core/backends/tart_macos.py`, launching macOS guest VMs with `--net-softnet --net-softnet-allow="${PROXY_IP}/32"`.
* Implement macOS `/etc/pf.conf` UID-to-port rule generation and dynamic Seatbelt `.sb` profile synthesis with Metal/IOKit GPU permissions (`AGXDeviceUserClient`).
* Implement APFS CoW cloning (`cp -c -R`) in `git_vault.py`.
* Build `pa-ios-runnerd` and the `ios-simulator` ACP package in `pa_packages/`, enabling background agent users (`agent1..N`) to build, install, inspect, and proxy-audit iOS applications inside `iOS Simulator`.

### Phase 4: Declarative `factory.toml` & Cloud Deployment (`pa factory deploy`)

* Introduce `factory.toml` configuration parsing alongside existing workspace configs.
* Implement `CloudRemoteBackend` (`pa_core/backends/cloud_remote.py`) to provision a remote Linux VM (via SSH or cloud API), deploy the external `coding-agent-proxy` sidecar, sync `factory.toml`, and expose `mitmweb`, `noVNC`, and **T3 Code** securely over Tailscale or Cloudflare tunnels.
